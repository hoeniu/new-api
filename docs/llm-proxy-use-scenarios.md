## 角色说明

| 角色 | 职责 |
|------|------|
| **平台管理员** | 建渠道、倍率、系统开关、用户与全局策略 |
| **租户 / 用户** | 在控制台创建 API 密钥、查看日志与额度 |
| **业务开发（终端用户）** | 用 `sk-xxx` 调 `/v1/chat/completions` 等，只关心 `base_url` + `model` |

下文「用户」若无特指，指**业务开发**；「管理员」指**平台管理员**。

## S1：一体机 / 多业务系统共用一个网关

### 背景

架构图中有多个业务平台（如 Text、龙虾等），各自希望调用大模型，但希望：

- 只维护**一套**上游连接与密钥；
- 在资源紧张的机器（一体机、边缘）上部署，避免每个业务各搭一套代理。

说明文档用**中央配置文件**驱动多个 LLM Proxy 实例；new-api 用**数据库 + 管理后台**承担同类职责。

### new-api 是否满足

| 项 | 结论 |
|----|------|
| 统一网关 | **有** |
| 单文件配置、极简进程 | **没有**（需 DB，功能更全） |
| 多实例读同一份「配置」 | **部分**：多实例 **共用同一数据库**（+ 可选 Redis）即可共享渠道/令牌 |

### 管理员操作步骤

1. 使用 `docker-compose` 或二进制部署 **一个** new-api + **SQLite/MySQL**（资源紧可用 SQLite）。
2. 配置 `.env`：`SQL_DSN`、可选 `REDIS_CONN_STRING`（若需 RPM/TPM）。
3. 在**渠道管理**中录入所有上游（本地 vLLM、公有云等），见 [S2](#s2-接入本地-vllm-与公有云模型)。
4. 为每个业务团队创建**用户账号**，或由管理员代发** API 密钥**（见 [S6](#s6-按-accesskey-限制-rpm--tpm)）。
5. （可选）再部署第二个 new-api 实例，`SQL_DSN` 指向**同一库**，实现多机入口、配置一处维护。

### 业务方如何使用

各业务把 OpenAI SDK 的 `base_url` 指向同一网关地址，使用各自分配的 Key，互不影响：

```bash
export OPENAI_API_BASE="https://<网关域名>/v1"
export OPENAI_API_KEY="sk-<该业务自己的令牌>"
# 之后与官方 OpenAI SDK 用法相同
```

## S2：接入本地 vLLM 与公有云模型

### 背景

说明文档 **Provider 管理** 要求：配置 `baseUrl`、`apiKey`、**模型协议**，以及模型 `id/name` 等。典型组合：

- 机房内 **vLLM**（OpenAI 兼容 `/v1`）；
- 外部 **OpenAI / Claude / 国内云** API。

需要在管理面登记多条 Provider，业务侧仍走统一入口。

### new-api 是否满足

**有**。等价能力为 **渠道（Channel）**：类型 = 协议，Base URL + 密钥 = Provider 连接信息。

| 说明文档 | new-api |
|----------|---------|
| provider name | 渠道 **名称**（自定义） |
| baseUrl | **Base URL** |
| apiKey | **密钥** |
| 模型协议 | 渠道 **类型** |
| 模型 id/name | 渠道 **模型列表** |

说明文档中的 `input`（文本/图）、Provider 级 `maxTokens`：**没有**独立配置项；`max_tokens` 由调用方在请求 body 传入。

### 管理员操作步骤

**本地 vLLM 示例**

1. **渠道管理** → **新建渠道**。
2. **名称**：`vllm-local`；**类型**：OpenAI 兼容（按实际选）。
3. **Base URL**：`http://127.0.0.1:8000`（或 vLLM 服务地址，通常需带 `/v1` 视部署而定）。
4. **密钥**：若 vLLM 未鉴权可填占位；有 Key 则填真实值。
5. **分组**：`default`（与后续令牌一致）。
6. **模型**：填写 vLLM 暴露的模型名，如 `Qwen2.5-7B-Instruct`。
7. **权重 / 优先级**：默认即可。
8. 保存。

**公有云示例（再建一条渠道）**

1. 再新建渠道，**类型**选对应厂商（OpenAI、Azure、Claude 等）。
2. **Base URL**、**密钥** 填云厂商控制台信息。
3. **模型列表** 填该账号可用模型 ID。
4. 同一 **分组** `default`，便于令牌一次访问多 Provider。

**（可选）模型广场展示**

1. **模型管理** → **添加模型**，填写与对外展示一致的名称与说明（不影响路由）。

### 业务方如何使用

直接请求**已在渠道中登记的模型名**（与 vLLM/云上 ID 一致，或见 [S5](#s5-对外统一模型名背后多上游模型聚合替代) 使用别名）：

```http
POST https://<网关>/v1/chat/completions
Authorization: Bearer sk-xxx
Content-Type: application/json

{
  "model": "Qwen2.5-7B-Instruct",
  "messages": [{"role": "user", "content": "你好"}]
}
```

查询可用模型列表：

```http
GET https://<网关>/v1/models
Authorization: Bearer sk-xxx
```

## S3：业务方使用 OpenAI 兼容 API（非聚合）

### 背景

说明文档 **模型代理** 中的「非聚合」：客户端请求的 `model` 与路由表一致，由代理选渠道转发，无需「模型池」抽象。

适用于：业务已选定具体模型（如 `gpt-4o`），网关负责鉴权、计费、选线路。

### new-api 是否满足

**有**。`/v1/chat/completions`、`/v1/embeddings` 等为标准路径。

### 管理员操作步骤

1. 完成 [S2](#s2-接入本地-vllm-与公有云模型) 渠道配置。
2. **系统设置 → 倍率**：为 `gpt-4o` 等配置**模型倍率**与分组倍率。
3. 为用户创建令牌（[S6](#s6-按-accesskey-限制-rpm--tpm)）：**分组** `default`，额度、RPM/TPM 按需。
4. 开启 **消费日志**（见 [S11](#s11-调用审计与日志清理)）以便对账。

### 业务方如何使用

Python 示例：

```python
from openai import OpenAI

client = OpenAI(
    api_key="sk-xxx",
    base_url="https://<网关>/v1",
)

resp = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "你好"}],
)
print(resp.choices[0].message.content)
```

**注意**：`model` 必须是令牌所属分组下、某条已启用渠道**模型列表**里存在的名称（除非使用 [S5](#s5-对外统一模型名背后多上游模型聚合替代) 的别名）。

## S4：同一模型名多渠道负载与主备

### 背景

说明文档未单独画「负载均衡」模块，但 **模型代理** + 多 Provider 时，常见需求是：

- 同一 `gpt-4o` 接 **多条线路**（不同代理商、不同区域）；
- **权重分流**或**高优先级主备**。

new-api 在 **`分组 + 相同 model 名 + 多渠道`** 上按权重/优先级选渠道，**不是**模型聚合（上游模型名仍相同）。

### new-api 是否满足

**有**。

### 管理员操作步骤

1. 新建渠道 A、渠道 B，**分组**均为 `default`，**模型列表**均包含 `gpt-4o`（**不要**对同一模型做不同 mapping，除非有意为之）。
2. 设置 **权重**：例如 A=`3`、B=`1` → 约 75% / 25% 流量。
3. **优先级**相同 → 负载均衡；若 B 优先级更低 → B 仅在 A 不可用或重试时参与。
4. 保存后检查渠道均为**启用**状态。

### 业务方如何使用

与 [S3](#s3-业务方使用-openai-兼容-api非聚合) 完全相同，仍传 `"model": "gpt-4o"`。  
用户**无感知**线路切换；管理员在 **使用日志** 中查看每次请求走的**渠道名称**。

## S5：对外统一模型名，背后多上游（模型聚合替代）

### 背景

说明文档 **模型聚合**：配置一个 **模型名称**，下挂 `1…n` 条 `{ provider, 模型名 }`，由代理统一路由、负载到 GPT、Claude、国产模型等。

典型场景：

- 对产品只暴露 `smart-chat`，内部替换不同厂商；
- 降本：按权重把流量分给便宜模型。

### new-api 是否满足

| 项 | 结论 |
|----|------|
| 管理面「模型聚合」配置页 | **没有** |
| 效果近似实现 | **有**（多渠道 + 每渠道 `model_mapping`，见 [对照文档附录 A](llm-proxy-spec-comparison.md#附录-a手工实现对外别名--多上游--负载均衡凑合方案)） |

说明文档 **Accesskey 类型：聚合 / 非聚合**：new-api **没有**该字段；只要渠道配好，任何 Key 传 `smart-chat` 均可走凑合方案。

### 管理员操作步骤

1. **定对外别名**：如 `smart-chat`。
2. **渠道 A（OpenAI）**  
   - 分组：`default`  
   - 模型列表：`smart-chat`（必须有）  
   - 模型重定向：`{"smart-chat":"gpt-4o"}`  
   - 权重：`3`
3. **渠道 B（Claude）**  
   - 分组：`default`  
   - 模型列表：`smart-chat`  
   - 模型重定向：`{"smart-chat":"claude-3-5-sonnet-20241022"}`  
   - 权重：`1`
4. **系统设置 → 倍率**：为 `smart-chat` 配置计费倍率（日志按对外名计费）。
5. **创建令牌**：分组 `default`；若开启模型限制，白名单包含 `smart-chat`。
6. **验证**：多次请求，在 **使用日志** 查看渠道是否在 A/B 间轮换。

**（可选）批量填模型名**：**模型管理 → 预填充分组** 建「模型分组」仅用于建渠道时一键填入列表，**不参与路由**。

### 业务方如何使用

只使用对外别名，**不要**传上游真实名：

```json
{
  "model": "smart-chat",
  "messages": [{"role": "user", "content": "写一段产品介绍"}]
}
```

`/v1/models` 是否列出 `smart-chat` 取决于各渠道模型列表是否只登记别名；建议**不要**把 `gpt-4o` 等同时写在列表里，避免暴露上游名（管理端会有提示）。

### 限制（须告知业务）

- 变更上游需改**多个渠道**，无单页「聚合池」。
- 失败重试可能从 GPT 切到 Claude，行为与说明文档「聚合池」可能不一致。
- 统计、计费均以 `smart-chat` 为准。

## S6：按 Accesskey 限制 RPM / TPM

### 背景

说明文档在 **Accesskey → 配额** 中配置 **RPM**（每分钟请求数）、**TPM**（每分钟 Token 数），超限则 **阻断**。

适用于：防止单个 Key 打满网关或上游；多租户 SaaS 按 Key 限速。

### new-api 是否满足

**有**。

| 字段 | 界面 | 含义 |
|------|------|------|
| `rate_limit_rpm` | **RPM 限制** | 近 60 秒滚动窗口内最大**请求次数** |
| `rate_limit_tpm` | **TPM 限制** | 近 60 秒滚动窗口内最大 **Token 数** |

**依赖 Redis**；填 `0` 表示不限。

### 管理员操作步骤

1. 部署并配置 `.env` 中 `REDIS_CONN_STRING`。
2. **控制台 → API 密钥**（或管理员为用户编辑令牌）。
3. 设置 **RPM 限制**。
4. 设置 **TPM 限制**。
5. 保存。

### 业务方如何使用

调用方式不变。超限时收到 **429** 类错误，文案含 RPM/TPM exceeded（以实际响应为准）。  
业务侧应实现**退避重试**，勿疯狂瞬时重试。

```python
# 无需额外参数；限速由服务端按 Key 识别
client.chat.completions.create(model="gpt-4o", messages=[...])
```

## S7：按 Accesskey 与按模型封顶用量

### 背景

说明文档配额还包括：

- **最大 token 数**、**最大请求数**（可按模型或按 Key）；
- 与 RPM/TPM 一起构成「硬封顶 + 速率」双层控制。

### new-api 是否满足

| 说明文档 | new-api | 说明 |
|----------|---------|------|
| 最大 token（Key 级） | **有** | 令牌 **剩余额度**（quota 单位），用尽拒绝 |
| 最大请求数 | **部分** | 令牌 **按模型配额** 中 `max_calls`（累计次数） |
| 按模型最大 token | **有** | `model_quota_limits` 中 `max_tokens` |

**没有**「按模型单独配 RPM/TPM」；RPM/TPM 为 **整 Key** 级别。

### 管理员操作步骤

**Key 总额度**

1. 编辑令牌，关闭「无限额度」，设置 **剩余额度**。
2. 用户每次调用扣减额度，至 0 拒绝。

**按模型累计上限**

1. 编辑令牌 → **按模型配额**（表格或 JSON）。
2. 每行：`model`（如 `gpt-4o`）、`max_tokens`、`max_calls`（`0` = 该项不限）。
3. 保存。

### 业务方如何使用

正常调用；触顶后返回 forbidden / 错误提示（额度不足或模型已达上限）。  
业务可在控制台 **使用日志** 或额度接口自行核对剩余量（若开放）。

## S8：仅允许指定模型（白名单）

### 背景

说明文档 **accesskey → 模型名称**：希望某个 Key **只能**调指定模型（或聚合名），防止越权调用昂贵模型。

### new-api 是否满足

**有**。**模型限制** + 可选 **按模型配额** 列表隐含允许的模型集合。

### 管理员操作步骤

1. 编辑令牌，开启 **模型限制**。
2. 勾选允许模型，如 `gpt-4o`、`smart-chat`（若用 [S5](#s5-对外统一模型名背后多上游模型聚合替代)）。
3. 保存。

### 业务方如何使用

```json
{ "model": "gpt-4o", "messages": [...] }
```

若传未授权模型，返回 **403**，提示模型不允许。  
用户侧只需保证 `model` 在管理员允许的列表内。

## S9：按 Accesskey 查看用量与统计

### 背景

说明文档 **访问量统计**：每 **10 分钟** 按 accesskey 统计：

- 请求数、请求 token；
- 响应数、响应 token。

用于运营看板、对账、排障。

### new-api 是否满足

| 项 | 结论 |
|----|------|
| 固定 10 分钟 + 四维表 | **没有完全一致** |
| 按次请求明细 + Token | **有**（消费日志） |
| 按用户/模型聚合 | **有**（`quota_data` + usage API，默认约 **5 分钟** 落库，可配） |

### 管理员操作步骤

1. **系统设置 → 运营**：开启 **消费日志记录**（`LogConsumeEnabled`）。
2. 确认 **数据导出** 开启（`DataExportEnabled`，默认常开），按需调整 `DataExportInterval`（分钟）。
3. 在 **日志管理**、**数据看板** 查看全局统计。
4. 集成侧：调用 `GET /api/usage/overview`、`GET /api/usage/by_model` 等（权限因角色而异），参见 `scripts/usage-prd-smoke.md`。

### 业务方（租户用户）如何使用

1. 登录控制台 → **使用日志**。
2. 按 **令牌名称**、时间筛选，查看单次 **prompt/completion tokens**、模型、渠道。
3. 仪表盘图表依赖管理员开启的数据导出。

**说明**：若必须「每 10 分钟一张 accesskey 四维表」，需从日志或 usage API **自行聚合**，无内置一键导出该口径。

## S10：超额自动阻断

### 背景

说明文档 **阻断**：accesskey 配额（RPM/TPM、最大 token、最大请求）触发后**自动拒绝**，无需人工下线 Key。

### new-api 是否满足

**有**。多种条件叠加判断（见下表）。

### 触发条件（无需单独开关）

| 条件 | 用户侧表现 |
|------|------------|
| 额度用尽 | 拒绝调用 |
| RPM / TPM 超限 | 429 类限流 |
| 按模型 `max_tokens` / `max_calls` 用尽 | 错误提示含模型名 |
| 模型不在白名单 | 403 |
| IP 不在白名单 | 403 |
| 无可用渠道 | 获取渠道失败 |

### 管理员操作步骤

组合配置 [S6](#s6-按-accesskey-限制-rpm--tpm)、[S7](#s7-按-accesskey-与按模型封顶用量)、[S8](#s8-仅允许指定模型白名单) 即可，**无需**单独启用「阻断」开关。

### 业务方如何使用

收到错误后停止或降速重试；联系管理员加额度或调高 RPM/TPM。  
**聚合别名**场景下，阻断仍按对外 `model` 与 Key 维度生效，与实际上游无关。

## S11：调用审计与日志清理

### 背景

说明文档 **日志**：

- 请求日志、响应日志 **分别开关**；
- **最大保留时长**、**最大保留条数**。

用于合规、排障与控制磁盘。

### new-api 是否满足

| 项 | 结论 |
|----|------|
| 请求/响应分开开关 | **没有** |
| 消费类调用日志总开关 | **有**（`LogConsumeEnabled`） |
| 按时间批量清理 | **有**（选手动时间点删除早于该时间的日志） |
| 按条数自动淘汰 | **没有** |

### 管理员操作步骤

1. **系统设置 → 运营维护 → 日志设置** → 开启/关闭 **消费日志记录**。
2. 选择 **清理早于某时间** 的日志 → 确认（一次性清理，非自动 TTL）。
3. 定期重复第 2 步，或自行用数据库任务清理（需运维规范）。

### 业务方如何使用

用户仅在控制台 **使用日志** 查看自己有权限的记录；**不能**单独打开「只记请求不记响应」。  
业务排障：提供时间、模型、`request_id`（若日志中有）给管理员查询。
