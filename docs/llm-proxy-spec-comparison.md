# LLM Proxy 架构说明 vs new-api 功能对照

> **使用场景、背景与分角色操作步骤**见：[llm-proxy-use-scenarios.md](llm-proxy-use-scenarios.md)  
> **部署售卖、单/多节点、PG+Redis、硬件与容量预估**见：[llm-proxy-deployment-guide.md](llm-proxy-deployment-guide.md)

---

## 总览

| 架构模块 | new-api 是否有同名/同等能力 | 一句话 |
|----------|---------------------------|--------|
| 轻量级一体机定位 | 部分 | 功能全、依赖 DB/Redis，非「单配置文件极简代理」 |
| 中央配置文件驱动多实例 | **没有** | 配置在数据库 + 环境变量，非共享一份配置文件 |
| Provider 管理（baseUrl/apiKey/协议/模型元数据） | **有（等价物：渠道）** | 见 §2.1 |
| **模型聚合**（一名称 → 多 Provider+模型） | **没有** | 见 §2.2；可用手工多渠道凑合 |
| Accesskey（聚合/非聚合类型） | **没有该类型字段** | 令牌/API Key 见 §2.3 |
| 配额 RPM / TPM | **有** | 见 §2.3；另见额度、按模型累计上限 |
| 模型代理（聚合/非聚合） | 部分 | 统一 OpenAI 兼容入口 **有**；聚合路由 **没有** |
| 按 Accesskey 每 10 分钟统计 | 部分 | 有日志/看板/usage API，粒度与字段不完全一致 |
| 按配额自动阻断 | **有** | 额度用尽、限流、模型上限等 |
| 请求/响应日志开关 + 保留条数/时长 | 部分 | 消费日志开关 + 按时间清理 **有**；分项开关/条数上限 **没有** |

## 1. 产品定位与部署架构

### 1.1 轻量级 LLM Proxy（一体机 / 资源紧张环境）

| 说明文档 | new-api |
|----------|---------|
| 强调轻量、适合资源紧张环境 | **部分满足**：可 Docker 单容器部署，但实际为完整网关（用户/计费/多渠道/前端），依赖 **SQLite/MySQL/PostgreSQL**，可选 **Redis**（令牌 RPM/TPM 等），资源占用高于「纯配置文件代理」。 |

**若需极简部署**：使用 `docker-compose` 仅起 `new-api` + 单库即可；无「仅一个 yaml 定义全部 Provider+聚合模型」的模式。

### 1.2 多应用 → 多 LLM Proxy → 中央配置文件

| 说明文档 | new-api |
|----------|---------|
| 多个业务方各自 Proxy，共用 **配置文件** 连接外部模型 | **没有**。配置落在 **数据库**（渠道、令牌、倍率等）+ **环境变量**（`.env`）。多实例若共用同一数据库，则等价于共享配置；**没有**架构图里的独立「配置文件」实体与导入导出为主流程。 |

**操作流程（多实例共享配置，近似做法）**

1. 多个 `new-api` 实例指向 **同一数据库**（与可选同一 Redis）。
2. 在任一实例管理后台改渠道/令牌，其他实例刷新缓存后生效（部分缓存有 TTL，渠道变更会触发缓存更新逻辑）。
3. 环境差异用各实例 `.env` 区分（如 `SQL_DSN`、`REDIS_CONN_STRING`）。

## 2. 管理 API

### 2.1 Provider 管理（baseUrl、apiKey、模型协议、模型 id/name/input/maxTokens）

| 说明文档字段 | new-api | 说明 |
|--------------|---------|------|
| baseUrl | **有** | 渠道 **Base URL** |
| apiKey | **有** | 渠道 **密钥**（支持多 Key） |
| 模型协议 | **有** | 渠道 **类型**（OpenAI、Claude、Gemini、Azure 等 40+） |
| 模型 id / name | **有** | 渠道 **模型列表**（逗号分隔模型名） |
| input（文本/图片） | **没有独立字段** | 模型元数据有 **端点类型**、标签等，无 Provider 级「input 能力矩阵」配置项 |
| maxTokens | **没有 Provider 级统一字段** | 上游 `max_tokens` 由客户端请求携带；令牌可配 **按模型累计 token 上限**（见 §2.3） |

**操作流程：新建一个 Provider（渠道）**

1. 管理员登录 → **渠道管理** → **新建渠道**。
2. 填写：**名称**、**类型**（协议）、**Base URL**、**密钥**。
3. **分组**：填写用户分组名（如 `default`），与令牌分组一致才能路由到该渠道。
4. **模型**：填写该上游支持的模型 ID 列表（如 `gpt-4o`）。
5. （可选）**模型重定向**：JSON，将对外名映射到上游名，例如 `{"smart-chat":"gpt-4o"}`。
6. **权重 / 优先级**：同分组、同模型名下多渠道时用于负载与主备。
7. 保存 → 系统自动写入 `abilities`（分组 × 模型 × 渠道）。

**操作流程：模型展示元数据（非 Provider 连接参数）**

1. **模型管理** → **添加模型**。
2. 填写 `model_name`、描述、图标、厂商、端点类型等。
3. （可选）**匹配方式**：完全 / 前缀 / 后缀 / 包含，用于定价页把多个渠道模型归到一条展示记录（**不改变路由别名**）。

---

### 2.2 模型聚合（一个模型名称 → 多个 Provider + 模型 1…n）

| 说明文档 | new-api |
|----------|---------|
| 管理面配置 **一个对外模型名**，下面挂多条 `{ provider, 模型名 }`，代理层统一路由、负载 | **没有该功能**。无「模型聚合」菜单、无 `聚合模型` 实体、无按聚合条目权重选上游。 |

**相关但不同的能力**

| 能力 | 是否有 | 说明 |
|------|--------|------|
| 模型分组（预填充分组） | 有 | 仅批量填充渠道模型列表，**不参与路由** |
| 模型元数据匹配规则 | 有 | 仅展示/定价归并，**不改变路由** |
| 同模型名多渠道 + 权重 | 有 | 负载在 **渠道** 间，要求对外 **同一 model 字符串** |
| 每渠道 model_mapping | 有 | 每渠道 **1 个别名 → 1 个上游** |

**没有时的凑合方案（手工多渠道 + mapping）**

详见下文 [附录 A](#附录-a-手工实现对外别名--多上游--负载均衡凑合方案)。

---

### 2.3 Accesskey 管理（映射模型、聚合/非聚合类型、配额）

| 说明文档 | new-api | 说明 |
|----------|---------|------|
| accesskey → 模型名称 | **有** | 对应 **令牌 / API Key**，通过 **分组 + 可用模型限制** 间接约束可调模型 |
| 类型：聚合 / 非聚合 | **没有** | 令牌无此枚举；不存在「聚合 Key 自动走模型池」 |
| 配额：RPM / TPM | **有** | 见下表 |
| 配额：最大 token 数 / 最大请求数 | **部分有** | 见下表 |

**new-api 令牌配额与限流对照**

| 配额项 | new-api 字段 | 操作流程 |
|--------|--------------|----------|
| **TPM** | `rate_limit_tpm` | 编辑令牌 → **TPM 限制**（需 Redis；`0` 不限） |
| **RPM** | `rate_limit_rpm` | 编辑令牌 → **RPM 限制**（需 Redis；`0` 不限） |
| 最大 token（全 Key） | **有** | 令牌 **剩余额度** / 是否无限额度；用尽拒绝请求 |
| 最大请求数 | **部分** | 令牌 **按模型配额** 中 `max_calls`（累计调用次数上限） |
| 按模型最大 token | **有** | 编辑令牌 → **按模型配额** → 添加行：`model` + `max_tokens` + `max_calls` |
| 可用模型白名单 | **有** | 令牌开启 **模型限制** 并勾选允许模型列表 |
| IP 白名单 | **有** | 令牌 **允许 IP** |
| 分组 | **有** | 令牌 **分组**（如 `default`、`vip`、`auto`） |

**操作流程：创建 Accesskey（API 令牌）**

1. **控制台** → **API 密钥**（或管理员为用户创建令牌）。
2. 设置 **名称**、**分组**（决定走哪批渠道的 `abilities`）。
3. 设置 **额度**（或无限额度）。
4. （可选）**RPM / TPM**：限制近 60 秒滚动窗口内请求数 / Token 数（`0` 表示不限，需 Redis）。
5. （可选）**模型限制**：仅允许列表内模型。
6. （可选）**按模型配额** JSON：每模型累计 `max_tokens`、`max_calls`。
7. 保存后使用 `sk-xxx` 调用 `https://<网关>/v1/chat/completions` 等接口。

**说明**：若说明文档要求 Key 绑定「聚合模型」一名称走多上游，new-api **需用附录 A 手工配置渠道**，且 Key 侧只看到对外别名（如 `smart-chat`），**没有**「聚合 / 非聚合」类型开关。

## 3. 模型代理（运行时）

### 3.1 支持聚合与非聚合模型代理

| 说明文档 | new-api |
|----------|---------|
| 明确区分聚合模型与非聚合模型转发 | **没有聚合模型类型**。**非聚合**：客户端 `model` 与渠道模型一致，直接路由。**近似聚合**：附录 A，非产品化能力。 |
| 统一 OpenAI 兼容 API | **有** | `/v1/chat/completions`、`/v1/models` 等 |

**操作流程：客户端调用（非聚合，标准路径）**

1. 使用令牌分组下渠道已登记的模型名，如 `gpt-4o`。
2. 请求头：`Authorization: Bearer <token>`。
3. Body：`{"model":"gpt-4o","messages":[...]}`。
4. 网关在对应分组下按权重/优先级选渠道 → 转发上游。

---

### 3.2 访问量统计（每 10 分钟 / accesskey：请求数、请求 token、响应数、响应 token）

| 说明文档 | new-api |
|----------|---------|
| 固定每 **10 分钟** 按 **accesskey** 统计四项指标 | **没有完全一致的口径**。 |

**new-api 现有统计能力**

| 能力 | 是否有 | 说明 / 操作 |
|------|--------|-------------|
| 按令牌的消费日志 | **有** | 需开启 **系统设置 → 运营 → 消费日志记录**（`LogConsumeEnabled`） |
| 日志字段含 prompt/completion tokens | **有** | **使用日志** 中查看单次请求 |
| 看板 / quota_data 聚合 | **有** | 需 `DataExportEnabled`；默认约 **每 5 分钟** 写入 `quota_data`（非 10 分钟，可配 `DataExportInterval` 分钟） |
| 按用户 usage API | **有** | 如 `GET /api/usage/overview`、`/api/usage/by_model`（管理员/用户权限不同） |
| 固定「每 10 分钟 + 仅 accesskey 四维表」 | **没有** | 需自行从日志或 usage 接口聚合 |

**操作流程：查看令牌用量**

1. 用户：**使用日志** 筛选令牌名称；或仪表盘图表（依赖数据导出）。
2. 管理员：**日志管理**、**数据看板**、用户/渠道统计页。
3. 接口集成：调用 `/api/log/self` 或 usage 系列接口（参见 `scripts/usage-prd-smoke.md`）。

---

### 3.3 阻断（按 accesskey 配额自动拦截）

| 说明文档 | new-api |
|----------|---------|
| 超过 accesskey 配额自动阻断 | **有**（多种机制叠加） |

**触发阻断的常见条件**

| 条件 | 说明 |
|------|------|
| 令牌额度耗尽 | `remain_quota <= 0` 且非无限额度 |
| RPM / TPM 超限 | 近 60 秒滚动窗口限流（需 Redis） |
| 按模型 `max_tokens` / `max_calls` 用尽 | `model_quota_limits` |
| 模型不在白名单 | `model_limits_enabled` |
| IP 不在白名单 | `allow_ips` |
| 用户/全局限流 | 中间件 `GlobalAPIRateLimit` 等 |
| 渠道全部不可用 | 无满足条件的渠道 |

**操作流程：配置「超额即拒绝」**

1. 编辑令牌：关闭无限额度，设置 **剩余额度**。
2. 设置 **RPM / TPM** 或 **按模型配额**。
3. 保存后，后续请求返回 403/429 类错误（以实际响应为准）。

**说明**：超限阻断由 **RPM / TPM** 检查实现；窗口为约 60 秒滚动累计。

---

### 3.4 日志（请求/响应开关、最大保留时长、最大保留条数）

| 说明文档 | new-api |
|----------|---------|
| 请求日志开关 | **部分** | 仅有 **消费日志总开关**（是否写入消费类日志），**无**单独「请求体日志」开关 |
| 响应日志开关 | **没有** | 无独立响应体日志开关 |
| 最大保留时长 | **部分** | 支持 **按时间点批量删除** 早于某时刻的日志，非自动 TTL 策略配置项 |
| 最大保留条数 | **没有** | 无「超过 N 条自动删最旧」的内置策略 |

**操作流程：日志与清理**

1. **系统设置 → 运营维护 → 日志设置**：开启/关闭 **消费日志记录**。
2. 同一区域选择 **清理早于某时间** 的日志 → 确认删除（一次性清理，非持续条数上限）。
3. 单次请求明细在 **使用日志** 查看（依赖上一步开关）。

## 附录 A：手工实现「对外别名 + 多上游 + 负载均衡」凑合方案

> 仅在说明文档 **模型聚合** 能力缺失时使用；**非官方功能**，维护成本高。

### 目标

客户端只调用 `model: "smart-chat"`，后端在 GPT / Claude 等上游间按权重分流。

### 步骤

1. **定对外别名**  
   例如：`smart-chat`。

2. **为每个上游建一条渠道**（§2.1）  
   - 渠道 A（OpenAI）：分组 `default`，模型列表含 `smart-chat`，模型重定向 `{"smart-chat":"gpt-4o"}`，权重 `3`。  
   - 渠道 B（Claude）：分组 `default`，模型列表含 `smart-chat`，模型重定向 `{"smart-chat":"claude-3-5-sonnet-20241022"}`，权重 `1`。

3. **配置计费**  
   **系统设置 → 倍率** 为 `smart-chat` 配置模型倍率（日志按对外名计费）。

4. **创建令牌**（§2.3）  
   分组 `default`；按需设额度、RPM/TPM、模型白名单（白名单需包含 `smart-chat`）。

5. **验证**  
   多次调用 `model: "smart-chat"`，在 **使用日志** 查看是否轮换渠道。

### 限制（必读）

- 无「模型聚合」配置页，变更上游需改多个渠道。  
- 负载均衡发生在 **渠道之间**，不是「一个配置项下多 Provider 条目」。  
- 失败重试可能切换到不同上游。  
- 计费、统计均以 **对外模型名** 为准。

## 附录 B：术语对照

| 说明文档 | new-api |
|----------|---------|
| Provider | 渠道（Channel） |
| 模型协议 | 渠道类型 |
| accesskey | API 令牌（Token / API Key） |
| 模型聚合 | **无**；近似：多渠道 + `model_mapping` |
| 分组（业务分组） | 令牌/渠道 **分组**（`default`、`vip` 等） |
| 模型分组 | 预填充分组（`PrefillGroup`，仅管理便捷） |
| RPM | `rate_limit_rpm`（60 秒滚动窗口） |
| TPM | `rate_limit_tpm`（60 秒滚动窗口） |
